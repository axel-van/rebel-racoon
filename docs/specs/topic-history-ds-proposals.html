Topic history — DS-compliant proposals

The .research-article Topic-history timeline in research-modals.renderHistory(). Three of its four parts are hand-built re-implementations of things the DS already ships. Below: what is non-compliant and why, then three proposals rendered live with real DS classes. Nothing is implemented in the app — this is a decision aid.

1 · What is non-compliant today

Part What it does now The rule it breaks
.topics-status +
--new/saved/used/ignored		 A hand-built pill: padding: 3px 10px, border-radius: 24px, 11px/800, uppercase, four hardcoded --ref-color-* fills. Re-creates .ap-status. The DS ships a pill-shaped status indicator with exactly these four colours. "Never hand-build a primitive that has a lookup entry."
.research-timeline__dot A 22px circle with a 3px white ring, filled by reusing the pill's background colour. Draws a dot the status pill already has. .ap-status::before is an 8px dot, shown by default, coloured per variant from --comp-status-*-dot-background-color. Two drawings of one idea, and the app's version borrows the background token for a dot, so they are not even the same colour.
.research-timeline__row ::before A 2px connector at left: 10px; top: 22px, hardcoded to the dot's geometry. Magic numbers, and a rail the DS has. .ap-stepper.with-line draws a 1px connector from --ref-color-grey-20. Every number here is derived from the hand-built dot, so the dot cannot change size without silently breaking the line.
__body / __when / __note font-size: 13px; --ref-color-grey-80 and grey-40. Off-scale type, reference tokens where semantic ones exist. 13px is not on the DS ramp (12 / 14 / 18). --sys-text-color-light is the semantic name for the greys used.

One thing is already right and should survive every proposal: the list is an <ol>. It is an ordered sequence of events and the markup says so.

2 · The colour mapping is free

The four review statuses map 1:1 onto .ap-status variants, so nothing needs a new token or a house rule. This is the single strongest argument for the rework: the DS already has every colour this feature invented.

Status Today (hand-built) DS variant Rendered
New grey-10 / grey-100 .ap-status.grey New
Saved tag-orange-20 / -150 .ap-status.tagOrange Saved
Used electric-blue-10 / -150 .ap-status.blue Used
Ignored red-10 / red-100 .ap-status.red Ignored

The reasoning recorded in brief-card.css for why Used is blue rather than green survives intact — .ap-status.blue is the DS's info/neutral colour, and green is taken by the Draft-ready tag. Adopting the DS component keeps that decision and stops maintaining it by hand.

4 · Proposal A — status pill only, no rail

Rendered · DS classes only

  1. New 2 weeks ago Surfaced from the competitor scan (1 matching item).
  2. New 3 days ago Re-scanned — 4 matching items, and a second account joined it.
  3. Used now Used to draft a post

Markup

<!-- one <li> per entry -->
<li class="p-row">
  <span class="ap-status grey">New</span>
  <span class="p-when">2 weeks ago</span>
  <span class="p-note">Surfaced from…</span>
</li>

What it removes

  • The hand-built pill → .ap-status with its own dot.
  • The 22px dot and its white ring — deleted, not replaced.
  • The ::before connector and all four of its magic numbers.

What it still needs

Three app rules, none of them a DS primitive: a flex row, a caption-size __when, and a body-size __note on its own line (flex-basis: 100%). All on DS tokens.

Cost

Loses the visual rail. For a three-to-five row list inside a dialog that is a small loss — the <ol> and the dates already say "sequence" — but it does read as a list of events rather than a path through them.

5 · Proposal B — .ap-stepper.with-line as the rail

Rendered · DS classes only

1 New 2 weeks ago Surfaced from the competitor scan (1 matching item).
2 New 3 days ago Re-scanned — 4 matching items, and a second account joined it.
3 Used now Used to draft a post

Markup

<div class="ap-stepper with-line">
  <div class="ap-stepper-item completed">
    <span>1</span>
    <span>… status + when + note …</span>
  </div>
</div>

What it removes

  • Everything Proposal A removes, plus
  • the connector is now the DS's (1px, --ref-color-grey-20, drawn by .with-line).

What it still needs

An override to stack vertically — .ap-stepper is a horizontal row, and the rendering above only stands up because of the inline flex-direction: column. That is app CSS on a DS class, which belongs in ds-patches.css if this is chosen.

Cost — and why I would not ship this

It asserts things that are false. A stepper is a progress indicator: numbered steps, completed / active / pending states, and a defined end. A topic's history has no step count, no final step, and no pending future — a re-scan can add a fourth entry tomorrow. Numbering "1, 2, 3" invites the reader to expect a step 4. The DS's own usage rule says stepper is "for multi-step flows, wizards, onboarding processes".

6 · Proposal C — status pill + a rail from the dot it already has

Rendered · DS classes + one app rule for the rail

  1. New 2 weeks ago Surfaced from the competitor scan (1 matching item).
  2. New 3 days ago Re-scanned — 4 matching items, and a second account joined it.
  3. Used now Used to draft a post

Rendered identically to A here on purpose: the rail is one ::before on the row, anchored to the pill's left edge rather than to a hand-built dot, and it is omitted above rather than faked with a magic number.

The one app rule

/* The rail hangs off the DS pill's own geometry:
   --comp-status-height (24px) is the only number,
   and it comes from the DS. No dot to sync with. */
.research-timeline__row:not(:last-child)::before {
  content: "";
  position: absolute;
  left: calc(var(--comp-status-height) / 2);
  top: var(--comp-status-height);
  bottom: 0;
  width: 1px;
  background: var(--ref-color-grey-20);
}

What it removes

  • The hand-built pill and the 22px dot, as in A.
  • The four magic numbers — the rail now derives from a DS token.

Cost

Keeps one decorative ::before in app CSS, and reads --comp-status-* — a component token, which the token rules say app CSS should not use directly. That is a real (small) violation to weigh against keeping the rail.

7 · Recommendation

Proposal A

Take A. It deletes all three re-implementations, needs no override of a DS class, and introduces no component token into app CSS. The rail is the only thing lost, and the rail was never carrying meaning — it connected dots whose colour merely repeated the pill beside them.

  • B is the wrong component. A stepper claims a step count and a final step; a topic's history has neither, and it needs a vertical override to render at all.
  • C is A plus a rail, at the price of one decorative pseudo-element and a --comp-* read in app CSS. Worth it only if the rail tests as load-bearing with a reader.

Whichever is chosen, two things carry over: keep the <ol>, and move __when / __note onto the DS ramp (12px caption, 14px body, --sys-text-color-light) so the 13px and the raw greys go with the rest.

Knock-on worth knowing before implementing: .topics-status is used only by this timeline (the feed card shows a glyph instead), so adopting .ap-status here lets the whole .topics-status block — the pill and its four colour rules, ~50 lines of brief-card.css — be deleted rather than left dormant.
